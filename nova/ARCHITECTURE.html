Protea Bank, end to end

A fictional South African bank that lets a customer's Claude read accounts and make payments, with the customer's phone as the final say on money leaving. This page describes every part, how they talk to each other, and what each one is trusted with.

Checked against the code and live deployments on 12 November 2026. Nothing here is real: no money, accounts or people.

Overview

Protea Bank is a Next.js site built on Poppyseed, an implementation of the Personal Agent Protocol (Poppy). Poppy defines how an AI agent, acting for a person, signs in to a company, what it may do there, and how the person approves what matters. Three things were added around the bank:

  • A bridge that makes Claude a Poppy agent. Claude talks MCP to the bridge; the bridge talks Poppy to the bank. Each person's agent sign-in is separate.
  • Curity as the identity provider for customers, staff, and the bridge's own users. The bank never holds a password.
  • An authenticator: an enrolled phone that approves agent payments with a fingerprint. The bank's side is built and live; the Android app is the next piece.

Components

  1. Claude calls the bridge over MCP (HTTPS, OAuth 2.1). Claude registers itself, and the customer logs in at Curity once to connect.
  2. The bridge calls the bank as a Poppy agent: a Session Key proves each request (DPoP), and the bank issues an Account Token per person once they approve.
  3. The bank reads the agent's public identity from the Worker (client.json, jwks.json) and checks the agent's signed assertions against it.
  4. The customer's browser: opens the sign-in link the bridge gave, approves scopes on the bank's page, adds a phone (QR), and uses the account pages.
  5. The browser signs in to Curity for the bank (customers and staff) and for the bridge's connector.
  6. The bank and the bridge exchange the login code with Curity on their own servers. Neither holds a password, and the bank keeps only a sealed cookie.
  7. The phone signs every request with a key that never leaves it, and signs an approval of one specific payment with a second key unlocked by a fingerprint.

Connecting Claude to the bridge

  1. Claude → bridgeThe customer adds https://mcp.proteabank.co.za/mcp as a custom connector. Claude registers itself as an OAuth client with the bridge.
  2. bridge → browser → CurityThe bridge sends the customer to Curity to log in. This identifies the person to the bridge (their Curity sub); it is not yet a sign-in to the bank.
  3. Curity → bridgeCurity returns to /auth/curity/callback. The bridge issues Claude its own token naming that person. Every tool call after that runs as that person only.

Signing an agent in to the bank

This is Poppy's Device Sign-In. The agent never sees the customer's credentials.

  1. Claude → bridgebank_sign_in. The bridge asks the bank to start a device sign-in for the scopes it wants (accounts:read, transactions:read, and payments:write when payments are allowed).
  2. bridge → bankThe request carries a client assertion signed with the agent's key (verified against jwks.json at the agent identity) and a DPoP proof from a fresh Session Key.
  3. bank → bridge → ClaudeA link and a short code. Claude shows them, then calls bank_wait_for_sign_in, which waits up to 45 seconds.
  4. customer's browser → bankThe customer opens the link, signs in with Curity, checks the code matches and sees the exact scopes and the agent's name and logo. Only the signed-in customer can approve.
  5. bridge → bankThe bridge's poll succeeds and it receives an Account Token. It keeps it encrypted. Any later bank call also finishes a sign-in approved since the last one.
  6. Claude → bridge → bankReads (list_accounts, list_transactions) run with the Account Token. Balances and transactions are separate scopes.

bank_sign_out revokes the token and calls the bank's internal end_all_sign_ins, which ends every sign-in that agent has for that person.

Paying

An agent can only propose a payment. A proposal becomes a payment only by a confirmation the bank accepts, and which one it accepts depends on whether the customer has a phone.

  1. Claude → bridge → bankpay_payee or a transfer between the customer's own accounts proposes an operation. Payees must already exist: an agent cannot add one.
  2. bank decidesThe approval policy checks whether this customer has an active phone, and the amount.
Customer hasAmountWho may confirm
an enrolled phoneanyThe phone only. The bank refuses the agent's confirmation with user_approval_required, even if it claims the customer approved. The website's approval page no longer approves either.
no phoneup to R500 to a saved payee, or up to R5 000 between own accountsThe agent, after the customer says yes in chat (bank_confirm_payment, sent as a standing permission). The bank applies the limit itself.
no phoneabove those limitsThe customer, on the bank's approval page, from the link in the proposal.

A payment moves money once: the operation id is the idempotency key, and funds are checked again when it is performed. A proposal lapses after 15 minutes. Proposing reveals whether an account could cover an amount, which the scope's description tells the customer when they grant it.

The phone

Enrolling

  1. customer's browserSigned in at the bank, the customer opens Account and presses "Add my phone". The page shows a QR code for protea://enroll?o=…&e=…&s=…, valid for 5 minutes and usable once.
  2. phone → bankThe app scans it, makes two P-256 keys in its secure hardware, and posts both public keys to /authenticator/enroll. The bank answers with a device id and a six-digit code.
  3. customerCompares the code on the phone with the one on the website and presses "The codes match", within 5 minutes. The device is inactive until then. Every enrollment failure is the same 400, so a guess learns nothing.

Approving a payment

  1. phone → bankThe app lists waiting operations. Every request is signed with the auth key over method, host, path, time, a one-time nonce and the body's hash. The bank checks the signature before it accepts the nonce.
  2. phoneShows the agent's name, the summary, the payee and the amount. It recomputes the hash of exactly what it shows and refuses to sign if it differs from the one the bank sent.
  3. customer → phoneFingerprint. This unlocks the approval key, which signs the origin, device, operation, revision, terms hash, nonce and time.
  4. phone → bankThe bank verifies the approval signature for exactly that revision and those terms, then performs the payment. A changed proposal gets terms_changed and must be shown again. Declining needs no fingerprint.

One device per customer. Replacing it is a staff action in the console. The full wire format is in AUTHENTICATOR.md.

What protects what

ThreatWhat stops it
An agent pays without the customerWith a phone, the bank refuses any confirmation not signed by the approval key. Without one, limits apply and larger payments need the customer's own approval.
A stolen agent tokenTokens are bound to a Session Key (DPoP). A token alone cannot be replayed from another machine.
One person's agent acting for anotherThe bridge's token names one Curity sub; each person has their own Poppy user id and encrypted state. Another customer's account looks like no account.
A replayed phone requestEach request has a time (within 2 minutes) and a nonce the bank remembers.
Tricking the customer into approving a different paymentThe approval signs a hash of the terms; the phone computes it from what it displays.
Someone else's phone enrolled to a customerQR is short-lived and single use; the customer must compare a code in their own signed-in browser.
A pretend staff memberStaff are the emails in STAFF_EMAILS, signed in through Curity. An emergency key exists and can only look at phones.
A site loaded in a frame or cachedframe-ancestors 'none' and no-store on account pages.
