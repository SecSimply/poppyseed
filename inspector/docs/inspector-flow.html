Poppy Inspector

How the Inspector works

The Inspector is a testing tool. It plays the part of an AI agent, introduces itself to a company's website, and shows every message that passes between them. This page follows one session against Protea Bank, a fictional bank in South Africa: from signing in, through the standard test run, to a full run in which a customer approves a payment.

Who is involved

  • YouSign in, press Run, approve what the agent asks of you and read the results. In the full run you are also the bank's customer.
  • The InspectorOur tool. It runs a real AI agent and records each exchange.
  • Identity providerCurity. It checks who you are, so the Inspector never handles your password.
  • Company siteThe website under test: Protea Bank, a fictional bank headquartered in Paarl. It decides whether to trust the agent, and what the agent may do.

Passwords stay put

Your password goes only to the identity provider. The Inspector receives a signed statement that you have signed in.

Every request is signed

Each request carries a signature and is tied to a key. A copied token is useless without the key that goes with it.

You see it all

Each exchange appears on screen. Tokens and signatures are masked on the server before anything reaches the browser.

Part 1

Signing in to the Inspector

Only people on a short approved list can use the Inspector, because it sends live requests to a real site. Sign-in uses OpenID Connect with PKCE, the standard way to sign in through an identity provider.

  1. A

    Start the sign-in

    What happens
    You open the Inspector. It sends your browser to the identity provider, along with a challenge it has just made up.
    What is sent
    The Inspector's name, a fingerprint of a random secret it keeps to itself (the PKCE challenge), and a random reference for this attempt.
    Why it is safe
    The fingerprint cannot be turned back into the secret. Only the Inspector can later prove it started this sign-in.
  2. B

    You sign in

    What happens
    You enter your credentials on the identity provider's own page. It sends your browser back to the Inspector with a one-time code.
    What is sent
    Your password goes to the identity provider and nowhere else. The code comes back through your browser.
    Why it is safe
    The code works once and means nothing on its own. Someone who copies it cannot use it without the Inspector's secret.
  3. C

    Swap the code and check it

    What happens
    The Inspector's server hands the code, its own client secret and the original random secret to the identity provider. It gets back a signed statement of who you are.
    What is checked
    The statement is signed by the identity provider, made for the Inspector, still fresh, and from this same sign-in attempt. Your email must be on the approved list.
    What you get
    A session cookie that the browser cannot read from page code. No tokens are kept in the browser.

Part 2

The standard run

Run journey performs seven steps against the bank. It needs no person. Each step builds on the one before. If a step fails, the run stops and shows the bank's own error.

  1. 1

    Discover the bank

    What is sent
    A plain request to a public address on the bank's site, /.well-known/poppy.json.
    What comes back
    The bank's business card: its name, which version of the protocol it speaks, which interfaces it offers and which permissions exist.
    Why it is safe
    It is public information. No credentials are involved.
  2. 2

    Read what the bank will not do

    What is sent
    A plain request for the bank's published list of tasks it does not offer to agents, such as adding a payee or closing an account.
    What comes back
    The list, each task with where to do it instead, such as at a branch or in the customer's own browser.
    Why it is safe
    An agent should know the limits before it starts. The list is the same for everyone and needs no sign-in.
  3. 3

    Start a session

    What is sent
    Two signed statements, one saying which agent this is and one giving the agent's identity with this bank. A single-use stamp ties the request to a fresh key made for this session.
    What comes back
    A session token that lasts an hour and is locked to that key. The bank first looks up the Inspector's public ID card and keys, which the Inspector publishes at its own address, to check the signatures.
    Why it is safe
    Each stamp can be used once, for one request. Without the key, a stolen token does nothing.
  4. 4

    List the tools

    What is sent
    A request to the bank's tool service, using a second token that works only for that service.
    What comes back
    The tools an agent may use: rates, branches, accounts, transactions, payees and payments, each with a short description and the permission it needs. The tool service follows MCP, the common standard for this.
    Why it is safe
    A token for the tool service is refused everywhere else.
  5. 5

    Use a public tool

    What is sent
    A request for the bank's savings rates. Like every request, it carries its own fresh stamp.
    What comes back
    The published rates, in rand.
    Why it is safe
    Anyone may use this tool. It touches no personal data and needs no sign-in.
  6. 6

    Ask the bank's assistant

    What is sent
    A question in the bank's support chat: what are your savings rates?
    What comes back
    An answer from the bank's assistant, which looked the rates up with the same public tool.
    Why it is safe
    A chat without a sign-in sees nothing personal. Asked for balances, the assistant asks for the permission and shows no numbers.
  7. 7

    Ask for something it will not do

    What is sent
    The first task from the bank's list, asked in plain words: add a new payee.
    What comes back
    The assistant declines, says where the customer can do it, and offers to pass them to a person.
    Why it is safe
    The bank keeps its promise on every interface, not only on paper.

What you see on screen

Each step shows a tick or a cross. Open a step to read every request and response behind it. When the bank refuses something, the likely causes are listed next to it. Each signed token is opened up, with its contents checked against the rules the bank applies. The signature itself is never shown.

Part 3

The signed-in run

Run with sign-in and operations adds the steps that need a person. This time you are the bank's customer. You approve a sign-in on the bank's own page, and the agent then reads your account, browses the site, chats, and proposes a payment. Nothing moves until it is confirmed, and the run ends by signing out.

  1. A

    Sign a customer in

    What is sent
    A request to sign a customer in, listing the permissions wanted: see accounts, see transactions, make payments.
    What comes back
    A short code and a link. You open the link on the bank's own page, check that its code matches the one on the Inspector's screen, read the permissions and approve.
    Why it is safe
    The agent never sees your password and gets only the permissions you approved.
  2. B

    Read the account

    What is sent
    A request for your accounts, using the signed-in session.
    What comes back
    Your balances, showing only the last four digits of each account number.
    Why it is safe
    It needs the see-accounts permission. A session without it is refused, and the refusal names the permission.
  3. C

    Browse the site

    What is sent
    The agent's browser proves it holds the session, then loads the account, payments, payees and staff pages.
    What comes back
    Your pages, showing only what the session's permissions allow. The staff page does not exist for an agent.
    Why it is safe
    The website follows the same rules as the tools, so it is not a back door.
  4. D

    Ask the assistant, then ask for a person

    What is sent
    A question about your account, then a request to speak to a person.
    What comes back
    The assistant answers from your account. The request puts the chat in the bank's staff queue, where a member of staff can take it over and reply.
    Why it is safe
    The assistant reads and explains. It never moves money in a chat.
  5. E

    Propose a payment

    What is sent
    A request to pay one of your saved payees, for example R1 735,00 to an electricity supplier.
    What comes back
    A proposal, not a payment: the bank says what it would do and waits.
    Why it is safe
    Nothing moves until the proposal is confirmed.
  6. F

    The person decides

    A small payment
    Within the standing permission you gave your agent, so it is confirmed without asking, and the Inspector says so.
    A large payment
    Over R5 000 the bank requires your own approval. The Inspector shows Approve and Decline. The agent confirms as you, and only after you click.
    Why it is safe
    The bank, not the agent, draws the line, and refuses an agent that claims a permission it was not given. An unanswered request declines after ten minutes.
  7. G

    Sign out

    What is sent
    A request to cancel the credential the agent was given.
    What comes back
    Confirmation that it is revoked.
    Why it is safe
    It happens whether or not the run finished, so no standing credential is left at the bank.

Part 4

When the bank says no

A bank decides what an agent may do, and who it will deal with. The Inspector shows both.

  1. 1

    Tasks the bank will not do for an agent

    What is sent
    Nothing is sent. The bank publishes the list (step 2 of the standard run): add a payee, close an account, send an international payment.
    What you see
    There is no tool for any of them. The assistant declines and says where to do it. On the website, the customer's own browser can add a payee, and an agent's browser is given no form.
    Why it matters
    A refusal that holds on every interface is one a customer can rely on.
  2. 2

    An agent the bank refuses

    How it is set
    Staff can block an agent by its address from the bank's support console.
    What you see
    The next run fails at the session step with client is blocked. The Inspector explains that this is the bank's decision, not a fault in the agent's keys.
    Why it matters
    A bank can refuse a particular agent, and an agent can tell that apart from a bug. A session already in hand runs until its token expires, an hour by default.

Beyond the runs

The Inspector can also send deliberately broken requests to confirm that a company refuses them: a forged signature, a stale stamp, a token for the wrong service. It reports whether the company said no, and how.

Terms used

Agent
Software that acts for a person, here an AI agent talking to a company's website.
Token
A digital pass the company issues after checking an agent. It is time-limited and limited in what it allows.
Signature
A mark that proves who produced a message and that nobody changed it.
Key
A pair of codes. One stays private and signs. The other is public and lets anyone check the signature.
Session
The period during which the company recognises the agent, tied to one key.
PKCE
A sign-in safeguard. It proves the program finishing a sign-in is the one that started it.
Approved list
The people allowed to use the Inspector, checked after the identity provider has confirmed who they are.
Permission
What a customer lets an agent do, such as see accounts or make payments. The bank checks it on every request.
Standing permission
Approval a customer gives in advance for small actions. Large ones still need the customer each time.
Excluded task
Something a company chooses not to offer agents, published with where to do it instead.
Blocked agent
An agent the company refuses by its address, whatever its keys.
MCP
A common standard for an agent to list and use the tools a service offers.
The identity provider and bank named here are the ones in the current test setup. Protea Bank is fictional: no real money, accounts or people. The diagrams show the runs as built.
